Ubuntu 将内核 SRU 周期缩短至两周，AI 自动化漏洞挖掘是主因

Canonical 将 Ubuntu 内核的稳定版更新（SRU）从原有的双轨制（每四周完整更新、两周安全更新）合并为单一的两周周期，由于新周期每周启动，实际实现每周发布一次内核更新。此举旨在应对 AI 和 LLM 将漏洞挖掘自动化后带来的海量内核缺陷，目标是在 CVE 公开后 24 至 48 小时内发布缓解措施。

Ubuntu 将内核 SRU 周期缩短至两周，AI 自动化漏洞挖掘是主因

Ubuntu 用户将因此更快获得内核安全修复。

迄今为止，Canonical 对 Ubuntu 内核一直采用分轨的 SRU 周期，常规修复和安全补丁分属不同轨道，每四周进行一次完整更新，并在两周中点发布一次针对紧急问题的安全更新。

如果你对这个概念还不熟悉，稳定版发布更新（Stable Release Update，简称 SRU）是 Canonical 在 Ubuntu 发布后向其推送缺陷修复和安全补丁的方式。内核在这方面拥有自己的专用轨道。

现在，Canonical 将两条轨道合并为单一的 2 周周期，并且由于每个新周期都在当前周期进行到一周时启动，这导致每周都会有一个内核版本发布。

每个周期从为期一周的补丁集成和准备工作开始。内核团队会挑选哪些修复进入每个内核，构建软件包，并运行基本冒烟测试，以便在构建继续推进之前发现任何明显问题。

第一周结束后，这些构建会被推送到 Ubuntu 的 proposed 仓库。内核发布候选版本在被认证之前就存放在那里，知道去哪里找的人可以访问，但尚未向普通用户开放。

第二周，Canonical 会让这些构建通过其硬件测试计划，在不同的机器类型上进行测试，以确保内核发布前在真实环境中不会出现问题。

无论当前周期进展如何，每周都会启动一个新周期，因此总有一个内核在完成测试并推出。这就是 2 周周期最终实现每周发布一次的方式。

而且，当某些东西不适合发布时，Canonical 表示他们会明确说明，并引导用户参考通用的系统加固建议。

对于无法等待整整两周的团队，Canonical 明确指向 proposed 仓库作为快速通道。其思路是你自己对放在那里的构建运行验收测试，而不是等待认证完成。

AI 自动化漏洞挖掘让这一变化不可避免

这一变化并非凭空而来；他们之所以不得不做出如此全面的决定，是因为 AI 自动化漏洞挖掘。就在上个月，我们看到它们仅仅通过抓取 git.kernel.org 来获取训练数据，就消耗了大量计算资源。

对 Canonical 而言，他们的决定是由 LLM 和 AI 代理推动的，这些技术将漏洞挖掘变成了一种自动化且不间断的行为，以个人类研究员无法复制的规模和速度发现内核缺陷。

目标是在 CVE 公开后 24 至 48 小时内发布一个临时解决方案。不是补丁本身，而是在补丁构建期间让受影响系统进入更安全状态的措施。

Ubuntu 背后的公司所做的，是通过缩短 CVE 公开到补丁落地之间的窗口，来应对快速演变的局势。
