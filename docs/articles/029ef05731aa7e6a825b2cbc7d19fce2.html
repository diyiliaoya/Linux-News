Linux 7.5 将可选阻止 /proc/kcore 访问以增强安全性

Linux 7.5 内核将引入新的启动参数 kcore=，允许在启动时可选禁用 /proc/kcore 访问。该文件可暴露系统物理内存和内核虚拟地址空间，仅限 root 或拥有 CAP_SYS_RAWIO 的进程访问。新选项默认开启，旨在为需要更高安全性的主机提供灵活控制，同时保留同一内核镜像用于调试等合法用途。

Linux 7.5 将可选阻止 /proc/kcore 访问以增强安全性

2026年11月19日 下午5:03 EST 发布。

一项已排队等待 Linux 7.5 合并窗口的补丁允许在启动时可选禁用 /proc/kcore 访问。这可以提升系统安全性，但对于典型内核构建，该功能默认仍保持启用。这个虚拟只读文件能够以 ELF 核心转储格式提供系统物理内存和内核虚拟地址空间的全部内容。/proc/kcore 文件确实有合法用途，例如实时内核调试、内存取证、ELF 检查等。对 /proc/kcore 的访问仅限于 root 或 otherwise 拥有 CAP_SYS_RAWIO 的进程，因为访问整个物理内存和内核虚拟地址空间是一件相当重要的事情。在 Linux 7.5 中，/proc/kcore 的访问将在启动时可选地进一步受限。

Chris Down 编写了一个补丁，允许通过 kcore= 启动参数在启动时禁用 /proc/kcore（前提是内核构建首先启用了 CONFIG_PROC_KCORE）。默认值为开启。Chris 在补丁说明中提供了理由：

“/proc/kcore 允许任何拥有 CAP_SYS_RAWIO 的进程读取所有内核内存。对于任何获得 CAP_SYS_RAWIO 的人来说，这是一个相当大的读取原语（而且它还会泄露 KASLR 布局）。

因此，在某些主机上我们希望关闭 /proc/kcore。就可读取的内容而言，/proc/kcore 并不比其他读取内核内存的方式更令人担忧，比如使用 CAP_BPF 和 CAP_PERFMON 的 BPF。区别在于，拥有 CAP_SYS_RAWIO 的进程不一定拥有 CAP_BPF 和 CAP_PERFMON，因为可能需要 CAP_SYS_RAWIO 进行硬件访问，而不一定想要授予通用 RAM 访问权限。CONFIG_STRICT_DEVMEM 已经使 /dev/mem 可以实现这一点，但 /proc/kcore 无论如何都提供了相同的通用 RAM 读取能力。

然而，在使用 CONFIG_PROC_KCORE=y 构建的内核上，目前阻止它的唯一方法是 lockdown=confidentiality（这还会禁用许多我们可能不想禁用的其他功能，比如 kprobes 和 bpf_probe_read_kernel()），或者使用 LSM。这很烦人，因为在大多数主机上，我们确实希望为 drgn/crash 等工具保持启用，所以今天我们构建了两个独立的内核。

让我们添加一个 “kcore=” 启动参数，以便可以在启动时禁用它，这让我们在使用同一内核镜像的同时保留这些选择。”

该补丁昨天被纳入 vfs/vfs.git 的 vfs-7.5.procfs Git 分支。随着这个 kcore= 选项的补丁现已进入 VFS 7.5 分支，预计它将在仅一个多月后举行的 Linux 7.5 合并窗口中被提交。
