Linux 7.3 引入两项令人振奋的内存管理优化

Linux 7.3 合并窗口期间，内存管理（MM）更新包含两项显著的性能优化。其一，针对 zsmalloc 内存分配器中的 zs_free() 函数减少锁竞争，在内存压力下可显著提升性能，测试显示树莓派 4B 速度提升达 1.83 倍，Intel 系统提升达 1.4 倍。其二，优化 rmap_walk_ksm 函数，解决 KSM 反向映射导致的严重性能问题，将锁持有时间从超过 500ms 降至不到 2ms，极大改善了高 VMA 共享场景下的应用延迟。

Andrew Morton 于周二提交了 Linux 7.3 合并窗口期间所有内存管理（MM）更新。本次 MM 拉取请求尤为庞大，他指出本周期发送了 1,250 封“added-to-MM”邮件，而上一周期为 920 封。由于补丁变更频繁，他还借助 Google 的 Gemini AI 撰写补丁摘要。在浏览这份冗长的 AI 生成摘要时，有两项补丁系列在性能方面令我感到兴奋。

首先是一个减少 zs_free() 中锁竞争的补丁系列。zs_free() 是 Linux 上 zsmalloc 内存分配器的一部分，被 Zswap 和 zRAM 用于释放压缩 RAM 页面。当系统处于内存压力下（无论是 Google Android 设备还是 Zswap 负载较重的服务器），zs_free() 中的锁竞争在取消映射路径中可能非常显著。鉴于当前内存价格下 Zswap/zRAM 使用量的增加（尤其是大型服务器），这一锁竞争优化可能非常有用。

在基准测试中，测量每个进程独立映射 256MB、写入数据、通过 madvise 将页面换出至 zRAM，然后并发取消映射的时间，发现 20 核 Intel 系统和小型树莓派 4B 均受益明显。小米的 Wenchao Hao 发现，在此操作中树莓派速度提升高达 1.83 倍，而 Intel 系统提升达 1.4 倍。

另外，同样属于 MM 拉取请求的一部分，还有针对 rmap_walk_ksm 的性能优化。rmap_walk_ksm 内存管理函数用于对通过内核同页合并（KSM）管理的页面执行反向映射遍历。ZTE 工程师发现 KSM 反向映射存在“严重”性能问题，在内存压力下应用程序可能冻结数百毫秒。当大量不相关的 VMA 共享同一个 anon_vma 时，该问题最为明显。

该问题如此严重，以至于锁持有时间从超过 500ms 降至不到 2ms！在最坏情况下，从 705ms 降至平均 1.44ms 或最大 1.67ms。

ZTE 的 Xu Xin 详细阐述了性能影响及一些实际案例：

1. 锁持有时间从 >500ms 降至 <2ms

- 在我们的基准测试中（20,000 个 VMA 共享一个 anon_vma），KSM rmap 遍历期间 anon_vma 锁的最坏持有时间从 705ms 降至 1.67ms（最大）和 1.44ms（平均）。

- anon_vma 锁也会被页面错误、回收、迁移、压缩、mlock、exit_mmap 和 cgroup 记账获取。

- 由于低效的 rmap 遍历导致的长时间锁持有会阻塞应用程序线程，造成延迟尖峰、吞吐量下降，甚至容器超时。

- 即使没有 fork() 也会发生此问题——VMA 分割（例如，通过 mprotect 或 madvise 随时间推移）可能创建数万个 VMA，全部附加到同一个 anon_vma。

- JVM / Go 运行时：它们使用 mmap 分配堆区域，随后调用 mprotect(PROT_NONE) 用于垃圾回收屏障或保护页，随时间将原始 VMA 分割成数千个小片段。

- 数据库引擎（MySQL、PostgreSQL）：大型共享内存缓冲区或匿名映射通过 madvise(MADV_DONTNEED) 管理以释放特定页面，这也会分割 VMA。

* 为什么基准测试数字是现实的：我们在一个运行 Java 应用程序且启用 KSM 的生产系统上观察到约 20,000 个 VMA 共享一个 anon_vma。补丁前，在内存压缩和页面迁移触发的 rmap 遍历期间，测得的锁持有时间最大为 228ms。基准测试在受控环境中重现了该 VMA 数量和锁持有行为。

对于每个 anon_vma 没有数千个 VMA 的系统，该补丁增加的开销可忽略不计（一次 pgoff 比较）。对于确实受此问题影响的系统，改进是显著的。
